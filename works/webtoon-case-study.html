01 — Overview

A platform for readers
and creators.

WebtoonHub is a full-stack digital comic platform that handles both sides of the content relationship: readers get an immersive reading experience with progress tracking and personalised discovery, and publishers get a full content management dashboard with analytics, scheduling and bulk upload support.

The challenge was building two very different product surfaces — one optimised for consumption, one for creation — on top of a single shared backend, without either side feeling like an afterthought.

02 — The Problem

Existing platforms
split the experience.

Most digital comic platforms are either reader-focused (optimised for consumption, no creator tools) or creator-focused (CMS-heavy, poor reading UX). Platforms that try to do both tend to bolt one side on as a secondary feature — you can feel it in the seams.

The goal was to design both surfaces from first principles, with a shared data model that made the publisher’s content decisions immediately visible to the reader without any synchronisation lag or manual publishing steps.

R
Reader needs
Smooth chapter-by-chapter reading with zoom and gesture support · Progress that syncs across sessions · Bookmarking and favourites · Discovery of trending and new releases
P
Publisher needs
Fast bulk upload with CBZ parsing · Episode management with scheduling · Engagement analytics per title · Content moderation tools

The design constraint: both surfaces had to feel like first-class products. The reading experience couldn’t look like a viewer bolted onto a CMS, and the publisher dashboard couldn’t look like a reader with admin buttons added.

03 — Architecture

One backend.
Two surfaces.

The entire backend runs on Supabase: PostgreSQL for structured data, Row Level Security for role-based access control, Supabase Auth for user management and Supabase Storage for comic assets. This kept operational complexity near zero while giving full relational database capabilities.

Frontend
React 18 + TypeScript
Component architecture with Framer Motion for animations, shadcn/ui for base components, Tailwind for utility styling. React Query manages all async state.
Backend
Supabase
PostgreSQL database with RLS policies scoped per role. Auth handles email/OAuth. Storage handles CBZ uploads and image serving with automatic CDN distribution.
Build
Vite + Vercel
Vite for fast local dev with HMR. Production deploys to Vercel with environment variables managed in the dashboard. Preview deployments on every PR branch.

04 — Reader Experience

Reading first.
Everything else second.

The reader interface is built around zero distraction. The chrome disappears when you start scrolling and reappears on pause or mouse movement. On mobile, swipe gestures advance chapters and pinch-to-zoom works natively without any gesture library.

01
Immersive reader
Auto-scroll mode advances the page at a configurable reading speed. Zoom state is persisted per-session so you don’t have to re-zoom every chapter. The reader viewport is sized to the comic frame, not the browser window.
02
Progress tracking
Reading position is written to Supabase on every chapter completion, not on every scroll event. This keeps write volume manageable while still resuming accurately at the chapter level. Last-read position is shown on the series card in the library.
03
Discovery
Trending is calculated from read counts in a rolling 7-day window. New releases are ordered by publication date with a “new” badge that expires after 14 days. Both feeds use React Query with a 5-minute stale time, so they stay fresh without polling on every render.
05 — Publisher Dashboard

Upload once.
Track everything.

The publisher dashboard is a separate route tree guarded by a role check on the Supabase session. Publishers see a different navigation structure entirely — library management, episode scheduling, analytics — with none of the reader-facing UI visible.

usePublisherGuard.ts — route protection 
// Role is stored in the Supabase user metadata on signup
export function usePublisherGuard() {
  const { user, isLoading } = useAuth();

  useEffect(() => {
    if (!isLoading && user?.role !== 'publisher' && user?.role !== 'admin') {
      navigate('/', { replace: true });
    }
  }, [user, isLoading]);

  return { isAuthorised: user?.role === 'publisher' || user?.role === 'admin' };
}
01
CBZ bulk upload
Publishers drag a CBZ archive onto the upload zone. The client parses it in a Web Worker, extracts page images, generates thumbnails and uploads to Supabase Storage in parallel batches of 4.
02
Episode scheduling
Episodes can be drafted and given a future publish date. A Supabase Edge Function runs on a cron schedule to flip draft episodes to published when their timestamp is reached.
03
Analytics dashboard
Per-title read counts, completion rates and bookmark counts visualised with Recharts. Data is aggregated in a Postgres view so the frontend query is a single fast SELECT.
04
Content moderation
Flagged episodes surface in a moderation queue with inline preview. Moderators can approve, reject or escalate without leaving the dashboard. All actions are logged to an audit table.
06 — Data Model

Schema designed
for both sides.

The database schema is the foundation everything else rests on. Getting it right upfront meant both the reader queries and the publisher queries could be written simply, without complex joins or denormalisation workarounds.

schema — core tables 
-- Series: one row per comic title
CREATE TABLE series (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  publisher   uuid REFERENCES users(id),
  title       text NOT NULL,
  status      text CHECK(status IN ('ongoing', 'completed', 'hiatus')),
  created_at  timestamptz DEFAULT now()
);

-- Episodes: chapters belong to a series
CREATE TABLE episodes (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  series_id    uuid REFERENCES series(id) ON DELETE CASCADE,
  chapter_num  int NOT NULL,
  publish_at   timestamptz,           -- null = draft
  page_urls    text[] NOT NULL
);

-- Reading progress: one row per user per series
CREATE TABLE reading_progress (
  user_id      uuid REFERENCES users(id),
  series_id    uuid REFERENCES series(id),
  last_episode uuid REFERENCES episodes(id),
  updated_at   timestamptz DEFAULT now(),
  PRIMARY KEY  (user_id, series_id)
);

Row Level Security on every table means the API client can query directly from the browser without a server layer. Readers can only read published episodes. Publishers can only write to their own series. Admins bypass all RLS. Zero custom auth middleware required.

"The backend shouldn’t be the reason the frontend is complicated. A well-designed schema means the UI code can be obvious."
07 — Challenges

What was harder
than expected.

01
CBZ parsing in the browser
CBZ files are ZIP archives. Parsing them synchronously blocked the main thread and froze the upload UI. Moving the extraction to a Web Worker was straightforward but required re-architecting the upload state to handle messages asynchronously. The result is a responsive progress indicator even on large files.
02
Optimistic UI for bookmarks
Toggling a bookmark should feel instant. React Query’s useMutation onMutate hook lets you update the local cache before the server responds, then roll back on error. Getting the rollback logic right with nested query keys took more iteration than expected.
03
Image loading on slow connections
Comic pages are large. On mobile on a slow connection, blank white space between page loads destroys the reading experience. A skeleton loader tied to the native onLoad event, combined with Supabase Storage’s image transform API for responsive sizes, kept pages feeling fast without reducing quality.
08 — Reflection

What I’d do
differently.

Start with the data model. I wrote the first version of the React components before the schema was finalised. When the schema changed (it always does), I had to rewrite components that had already been tested. Schema-first development would have saved time here.

Feature flags earlier. The publisher dashboard was built in a feature branch and merged all at once. A feature flag on the role check would have let me ship incrementally and test individual dashboard sections in production with a small group.

Abstract the Supabase client sooner. Direct Supabase client calls were scattered across components before I centralised them into custom hooks. The refactor was worth it — the hooks are testable and the components became much simpler — but it would have been easier to start with that pattern.

Accessibility from the start. The reader keyboard navigation (next/previous chapter, zoom) was added after the fact. It worked, but threading aria- attributes and focus management through an existing component tree was messier than building it in from the beginning.
