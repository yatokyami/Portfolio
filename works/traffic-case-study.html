01 — Overview

Predict congestion.
Not just report it.

Most traffic applications tell you what is happening right now. This project was about building a system that tells you what is going to happen in the next 30 to 90 minutes — with enough confidence and specificity to be actionable for both individual commuters and city traffic management authorities.

The system fuses three data streams — historical traffic patterns, live sensor feeds and weather reports — and passes them through a prediction pipeline to produce congestion forecasts displayed on an interactive map dashboard with route alternatives and configurable alert thresholds.

02 — The Problem

Traffic data exists.
Prediction doesn’t.

Cities generate enormous volumes of traffic data from sensors, cameras and GPS traces. Very little of it is used predictively. Navigation apps report current conditions; some estimate arrival time based on typical patterns. But granular, near-term congestion forecasts — “this corridor will become severely congested in 40 minutes based on the current rate of inflow” — aren’t available to commuters or city planners at the resolution that would make a material difference.

C
Commuter perspective
By the time a navigation app tells you a route is congested, you’re already in it. A 30-minute forecast lets you make a route decision before you leave, not after you’re stuck.
A
Authority perspective
Traffic management centres react to incidents. Predictive congestion data lets them proactively adjust signal timing, deploy traffic officers and update variable message signs before a bottleneck forms rather than after.

The core technical challenge was not the ML model itself — there is significant literature on traffic forecasting. The challenge was building a pipeline that keeps the model fed with clean, normalised data from heterogeneous sources in near-real-time, and surfacing the output in a dashboard that actually communicates uncertainty rather than projecting false precision.

03 — Data Pipeline

Three sources.
One clean feed.

The prediction model is only as good as its inputs. Before any ML work, the majority of development time went into building a reliable ingestion and normalisation pipeline that could handle the inconsistency of real-world data sources.

01
Ingest
Historical CSVs loaded on startup. Live feeds polled every 60 s via REST. Weather data fetched every 15 min from OpenWeatherMap.
02
Normalise
Timestamps aligned to UTC. Speed values normalised to km/h. Missing sensor readings filled with rolling 5-minute averages. Outliers clipped at 3σ.
03
Feature engineering
Time-of-day, day-of-week and holiday flags added. Weather severity score computed from precipitation + visibility + temperature delta. Rolling 15-min average speed per corridor computed.
04
Predict
Gradient-boosted model (XGBoost) trained on 6 months of historical data. Inference runs every 5 minutes. Outputs congestion level (0–4) and confidence interval per corridor per time step.
05
Serve
Predictions stored in Redis with a 6-minute TTL. Express API serves map tiles and forecast data. WebSocket pushes threshold alerts to connected dashboards.

def predict_corridor(corridor_id: str, horizon_steps: int = 18) -> list[CongestionForecast]:
    """
    Returns a list of CongestionForecast objects, one per 5-min step up to
    horizon_steps (default 18 = 90 min ahead).
    """
    features = feature_store.get_latest(corridor_id)
    forecasts = []

    for step in range(horizon_steps):
        X = build_feature_vector(features, step)
        level = model.predict(X)[0]
        confidence = model.predict_proba(X).max()
        forecasts.append(CongestionForecast(
            corridor=corridor_id,
            t_plus_min=(step + 1) * 5,
            level=int(level),
            confidence=round(float(confidence), 3)
        ))

    return forecasts
04 — Dashboard Design

Two audiences.
Two views.

The commuter view and the city authority view share the same underlying data but present it at different scales. Commuters need route-level information: “is my route going to be clear in 30 minutes?” Authorities need corridor-level aggregation: “where should we adjust signal timing in the next hour?”

01
Interactive map (Mapbox GL)
Corridors are colour-coded by predicted congestion level: green (free flow), amber (moderate), red (congested), dark red (severe). A time scrubber lets users step through the forecast window 5 minutes at a time. Selecting a corridor shows the confidence interval as a shaded band on the forecast chart.
02
Commuter route planner
Enter origin and destination. The system calculates 3 candidate routes and shows the predicted travel time for each at your chosen departure time, including congestion risk as a probability band. Alternate route suggestions surface automatically when the primary route is predicted to be severely congested.
03
Authority alert dashboard
Threshold-based alerts with configurable severity and corridor scope. Authorities set a congestion level and a time window; the system sends a WebSocket push the moment a predicted value crosses the threshold. Alert history is logged with confidence score and actual outcome for model calibration.
04
Historical analytics
Recharts visualisations of corridor performance over time: weekly and monthly congestion patterns, worst-performing corridors, prediction accuracy vs. actual outcomes. The accuracy charts are important — they make the model’s confidence levels legible to non-technical users.
"The model was the easy part. Getting three messy data sources to agree on what time it is took longer."
05 — Tech Stack

Chosen for the
problem, not the hype.

Python for the ML pipeline. The data science ecosystem (pandas, scikit-learn, XGBoost) is simply the best tooling for this problem. The prediction service runs as a standalone Python process with a lightweight Flask API, keeping the ML code completely decoupled from the Node.js backend.

Redis for forecast caching. Predictions run every 5 minutes. Serving them from Redis means the API response time is sub-10 ms even under load, and the prediction service isn’t hammered by every map interaction.

Mapbox GL JS for the map. Colour-coding thousands of corridor segments in real time requires vector tiles and GPU-accelerated rendering. Leaflet wasn’t fast enough. Mapbox GL’s data-driven styling means corridor colours update with a single setFeatureState call — no re-render, no DOM manipulation.

WebSockets for alerts. Polling a “check alerts” endpoint every 30 seconds would have been simpler, but for the authority dashboard a 30-second delay on a congestion alert is unacceptable. Socket.io with room-based subscriptions means each authority only receives alerts for the corridors they manage.

06 — Challenges

What didn’t go
to plan.

01
Weather data lag
OpenWeatherMap’s free tier updates every 10 minutes, but the paid tier updates every 1 minute. The model was trained on 10-minute weather data, but the live feed sometimes arrived stale due to API caching on their end. When weather was changing rapidly, the forecast accuracy dropped noticeably. The fix was to weight the weather feature down when its freshness exceeded 12 minutes.
02
Sensor drop-outs
Real traffic sensor networks have drop-outs — sensors go offline, report zeros, or report the same value repeatedly. A naive pipeline treating dropped sensors as valid readings would produce prediction spikes. Adding a sensor health check that flags readings as suspect when they deviate more than 3σ from the rolling corridor mean eliminated the worst outliers.
03
Communicating uncertainty
The model outputs a confidence score alongside the predicted congestion level. Early dashboard designs just showed the congestion level and ignored the confidence, which meant users were treating a 55% confidence “moderate congestion” prediction the same as a 92% one. Adding a confidence band to the corridor tooltip and greying out low-confidence predictions on the map changed how people used the data.

Model accuracy on test data: ~83% correct congestion level at t+30 min, ~71% at t+90 min. These numbers are presented alongside the forecast on the authority dashboard so operators can calibrate their trust in the output rather than treating it as ground truth.

07 — Reflection

What I’d build
differently.

Start with a simpler model. XGBoost was chosen early because it’s well-understood for tabular data, but a simpler baseline (linear regression on rolling averages) would have been faster to validate and almost as accurate in the 0–30 minute window. Complex models should follow a working simple model, not precede it.

Abstract the data sources earlier. The first version had OpenWeatherMap API calls scattered across the pipeline. When the provider rate-limited the app during a demo, every module that touched weather data broke simultaneously. A centralised data source registry with fallback behaviour would have been 2 hours of work upfront that would have saved an embarrassing demo moment.

Design the alert UX before the alert system. The threshold alert feature was built technically before anyone had decided what the alert UI should look like. The result was a technically functional alert system with a confusing UI that required two redesigns. The interface should be prototyped before the backend is built — not the other way around.

Ship the commuter view first. The authority dashboard was built in parallel with the commuter view, which doubled the UI surface area before either was fully tested. Shipping the commuter view alone, getting feedback, then building the authority view on top of a stable base would have been faster overall.
