01 — Overview

A hospital’s entire
operation. Live.

CuraNet is a comprehensive real-time hospital management system built to replace the patchwork of disconnected tools that most hospital operations rely on. Bed tracking, OPD queue management, blood bank inventory, patient admissions, medical supplies — all of it unified in a single dashboard, with live updates across every device on the network.

The core premise was that hospital staff shouldn’t be chasing each other for status updates. Every change — a bed becoming available, a patient admitted, a blood unit requested — should propagate instantly to every role that needs to know about it.

02 — The Problem

Hospital operations
are fragmented.

Hospital operations typically involve a dozen disconnected systems: a separate bed management tool, a manual OPD token queue, a spreadsheet for blood bank inventory, and a patient records system that nobody can access from the ward. Staff spend time chasing each other and second-guessing data that’s already stale.

The cost of bad information in a healthcare environment isn’t a slow feature — it’s a delayed bed assignment, a missed blood unit, a patient waiting in the wrong queue. CuraNet was built to make the real-time state of a hospital floor legible to every person who needs to act on it.

01
No shared source of truth
Each department maintains its own records independently. A bed listed as occupied in one system might show as available in another. Nurses spend time on phone calls to verify what a dashboard should just show them.
02
Manual queue management
OPD tokens are typically paper-based or managed in a basic POS system with no digital visibility. Patients have no way to know their wait time, and doctors have no way to see queue depth without walking to the reception desk.
03
Reactive rather than predictive
Hospitals react to resource shortages rather than anticipating them. Blood inventory runs low before an order is placed. Beds fill up before wards are staffed up. The data to predict these events exists — it just isn’t connected anywhere.
03 — Role-Based Dashboards

One system.
Four perspectives.

Every role in CuraNet sees a completely different interface, scoped to what they actually need to do. This wasn’t a design flourish — showing a nurse the admin billing interface, or a patient the blood bank management screen, would be actively harmful. Role boundaries are enforced at both the UI level and the Firebase RLS level.

Admin
Full system oversight
Hospital-wide statistics, user management, resource allocation controls, financial analytics and system configuration. The admin dashboard is the only surface with write access to every module.
Doctor
Clinical workflow
Patient list for the current shift, OPD queue for their department, prescription and note entry, bed assignment for admissions, lab result access. No billing, no inventory, no blood bank.
Nurse
Ward management
Live bed status for their ward, patient vitals entry, medication administration records, shift handover notes. Nurses can see OPD queue depth but cannot modify it.
Patient
Personal portal
Appointment booking, personal medical records, prescription viewing, lab results, payment history. Read-only on everything except appointment creation. Zero access to other patients’ data.
04 — Architecture

Firebase at the
centre.

The core data model lives in Firebase Realtime Database. Every module that needs live updates — beds, OPD queues, blood bank — is a Firebase listener. Changes written by any client propagate to all connected dashboards in under 200 ms without polling.

A Node.js/Express backend sits in front of Firebase for operations that require server-side logic: authentication token validation, complex aggregations for the analytics dashboard, SMS notification dispatch and the predictive resource allocation calculations that run on a schedule.

bedService.js — real-time bed listener 
// Single listener keeps the entire bed map in sync across all clients
export function subscribeToBeds(wardId, callback) {
  const ref = db.ref(`beds/${wardId}`);

  ref.on('value', snapshot => {
    const beds = snapshot.val() ?? {};
    // Normalise to array, attach ward metadata
    callback(Object.entries(beds).map(([id, data]) => ({
      id,
      ...data,
      wardId,
      isOccupied: data.status === 'occupied'
    })));
  });

  // Return unsubscribe so React effects can clean up
  return () => ref.off('value');
}

05 — Key Modules

Eight systems.
One interface.

01
Smart OPD system
Token-based queue with department-wise organisation. Tokens are issued digitally and patients receive SMS updates with estimated wait times. Doctors see their queue depth in real time and can mark patients as “called” or “no-show” from their dashboard.
02
Real-time bed management
Live grid view of every bed in every ward. Status colours: available (green), occupied (red), cleaning (amber), maintenance (grey). Patient assignment, transfer and discharge all update the grid instantly via Firebase. Bed utilisation analytics are aggregated per ward.
03
Blood bank management
Inventory tracking by blood type and unit count, with expiry date monitoring. Donation camp management. Emergency allocation flow that surfaces nearest available units matching a request. Low stock automatically triggers a reorder notification to the admin.
04
Emergency response
Ambulance location detection (placeholder for GPS integration), outbreak monitoring tied to admission diagnosis codes. City-wide heatmap visualisation showing regional healthcare demand, built on aggregated anonymised admission data.
05
Analytics dashboard
Hospital performance metrics: patient flow, bed occupancy rate, average length of stay, OPD throughput, inventory burn rate. All visualised with Recharts, backed by Postgres aggregation views that run on a 15-minute refresh schedule.
06 — Data Structure

Schema designed
for real-time reads.

Firebase Realtime Database is a JSON tree, not a relational database. Schema design required thinking in terms of read patterns first, because deep nesting or large objects will always return more data than you need. The top-level keys map one-to-one with the modules in the UI.

firebase — top-level schema 
{
  "patients": {
    "patientId": {
      "personalInfo": { ... },
      "medicalHistory": { ... },
      "appointments": { ... }
    }
  },
  "opdQueue": {
    "tokens": [
      { "tokenNumber": "A101", "patientId": "p123",
        "status": "waiting", "department": "General Medicine" }
    ]
  },
  "beds": {
    "bedId": {
      "status": "occupied", "patientId": "p123",
      "ward": "ICU", "bedNumber": "A-101"
    }
  },
  "bloodBank": {
    "inventory": {
      "A+": { "units": 25, "lastUpdated": "2025-01-01" }
    }
  }
}

Denormalisation is intentional. Patient name is stored on the bed node even though it’s also on the patient node. This means reading the bed grid requires exactly one Firebase read — no joins, no secondary lookups, sub-50 ms render for a 200-bed ward view.

07 — Challenges

What pushed
back.

01
Firebase listener cleanup
Forgetting to detach Firebase listeners when React components unmount creates memory leaks that accumulate silently. Centralising all listener subscriptions in custom hooks with cleanup functions returned from useEffect solved this, but it required auditing every component that had a live subscription.
02
Concurrent writes to the queue
Two receptionists issuing tokens simultaneously could assign the same token number if both read the current counter before either had written. Firebase transactions (atomic read-modify-write) fixed this, but they required restructuring the token assignment flow to use server-side logic rather than client-computed values.
03
Role enforcement across two backends
Firebase Security Rules enforce role access at the database level, but the Node.js API also needs to enforce roles for aggregation queries. Keeping both rule sets in sync as the schema evolved was tedious. A shared constants file for role names was a small fix that prevented a class of subtle bugs.
04
Offline behaviour
Firebase’s offline persistence is on by default, which means reads still work when the network drops — but writes queue locally and sync when reconnected. For a hospital environment, stale reads can be dangerous. Implementing connection state detection and showing a clear “offline” banner took priority over any other UX refinement.

to v2.0.0

Initial release with bed tracking, OPD queue, blood bank inventory and basic patient admissions. Static data; no real-time sync. Role-based routing in place but enforced only on the frontend.
v1.5.0
Smart OPD + patient portal
OPD queue rebuilt with token generation and department routing. Patient portal added with appointment booking and record access. Firebase Realtime Database introduced for the queue module only.

Full Firebase integration + real-time everywhere
All modules migrated to Firebase. Socket.io added for instant push notifications. Emergency response module and city-wide heatmap added. Predictive resource allocation introduced using rolling 30-day admission averages. Backend separated into Express service with JWT auth.
09 — What I’d Do Differently

Honest
retrospective.

Firebase Security Rules from day one. In v1, role enforcement existed only in the frontend. A user who inspected the Firebase URL could read any node. The v2 migration added proper Security Rules, but retrofitting them onto an existing schema is harder than writing them alongside it.

Design system before components. The four role dashboards were built sequentially, so the early modules look subtly different from the later ones. A shared component library would have kept them visually consistent without the manual audit pass that v2 required.

Separate read and write models. The Firebase schema was optimised for reads (denormalised, flat), which made writes complex — updating a patient’s name requires touching 4 different nodes. A CQRS-style separation would have kept the read model fast while keeping writes simple.

Test the offline case explicitly. Offline behaviour was discovered by accident when a demo was run on a flaky conference WiFi. It worked because Firebase handles it, but the UX for degraded state should have been designed deliberately, not stumbled into.
